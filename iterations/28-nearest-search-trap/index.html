THE NEAREST-SEARCH TRAP

A proof in the grid engine plants two mapped nodes around one query point: a true nearest node almost due east, and a decoy almost due north. A search that scans every node finds the true one. A search that first cuts the map to a square box drawn in degrees can silently keep the decoy and drop the true node, because a degree of longitude is shorter than a degree of latitude away from the equator. Every distance below is returned by the engine's own modules, called in this page.

      Questions

      1. How does this help draw a system or a single-line diagram?

      It feeds one element: the far end of a cable route, the substation node at the network end of an onshore connection. index(points).nearest(lon, lat, { minimumKv }) returns { point, km }: point.name and point.location name and place that node, point.voltages_kv gives the voltages its busbars declare, and km is the straight-line length from the site. It draws no busbar, transformer, protection or earthing, and no route: the length is a straight line, not a cable length. Cited: gridmachine1 CABLE-ENGINES.md (commit c6cbf96), "Onshore connection" row, endpoints "site, substation", measuring "distance to the nearest mapped substation at or above the relevant voltage".

      2. What is this code used for?

      Module engine/v9-nearest-search.js in ventus-grid-engine at commit d9cd18b, exporting normalise, index and schema; it imports distanceKm from engine/v9-geodesy.js. Package export ./v9-nearest-search (package.json). Callers inside the engine at that commit, by source: proofs/v9-engine.proof.mjs (the trap on this page) and proofs/compute-observer.proof.mjs (a fixture lookup). It was extracted from gridatlas atlas/modules/202609011950-substation-lookup.js, which its own header and sources/provenance.json record as in no composition manifest, so nothing in the live Atlas loads it. The live Atlas runs an inline, byte-different exhaustive duplicate, state.nearest at line 6083 of gridatlas atlas/cartridges/202609041330-substation-intelligence-v9-63.js (commit 64268fd), documented in the engine's docs/v9-duplication.md 2(a). A text search of gridatlas outside releases/ for .nearest( found no call of that function by name, only network.nearest in the SLD sandbox cartridges, a different index (name-match inference).

      3. Where does it lead next?

      The next element is the cable route from the site to that node, and at the node, the substation busbar of the voltage asked for. In the estate's engine routing (gridmachine1 CABLE-ENGINES.md) this search is E1, "substation finder within a radius", the general case and the declared fallback for offshore wind (E3) and declared transmission connections (E4). A route model, busbar group or rating for that node is not established here: this module returns a name, a place and a distance, and nothing else.

      Machine detail · inputs: points [{ name, location { lon °, lat ° }, voltages_kv [kV] }], query lon ° and lat ° (decimal degrees), minimumKv kV (floor on the highest declared voltage; default 0), limit count (default 1; 0 is read as 1) · outputs: { point, km } or null for limit 1, else an array sorted by km ascending; km is haversine on a sphere of radius EARTH_RADIUS_KM km; index also returns size (distinct normalised names), located (points with a location), byName(name) → point or null · refusals: none thrown; no eligible node returns null, a node with no voltages is skipped, a point with no location is never searched · source: ventus-grid-engine d9cd18b0e2034325814924e6e4a0e958014f2748.
